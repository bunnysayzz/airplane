# PL2 macOS spike: go/no-go verdict (2026-11-03)

Base audited: main head `6001008f` (app 0.1.17, React Native 0.79.7,
Expo SDK 53). This is a spike, not a target: no `macos/` scaffold is
committed on this branch, because a macOS target cannot be built or
verified on Linux (it needs Xcode and a Mac), and an unbuildable
scaffold would be dead weight. The queue item asked for a time-boxed
spike with a go/no-go verdict before any target work. This document
is that verdict.

## Verdict: NO-GO for a full-parity macOS app

A macOS app with feed, posting, BLE mesh relay, and location-cell
scoping is not achievable by carrying the mobile stack over. A
Nostr-only viewer (feed reading plus relay posting, no BLE mesh, no
cell scoping) is feasible, but it must never be presented as the
Airplane app: without BLE advertising and without location cells it
loses the two things that define the app.

## Decisive blockers

1. The fork changed. The ptmt `react-native-macos` fork named in the
   original plan is no longer maintained. The live fork is
   Microsoft's `microsoft/react-native-macos`, whose getting-started
   guide uses 0.81.2. Airplane is on React Native 0.79.7, so a macOS
   target starts with a React Native upgrade (0.79.7 to 0.81 or
   later), not with a new target folder.
   Source: https://microsoft.github.io/react-native-macos/docs/getting-started
2. Expo modules on macOS are experimental, not first-class.
   Microsoft's guide states: "macOS support for Expo modules is
   currently experimental", via `use_expo_modules!`. Expo SDK 58
   notes say macOS is not supported until `react-native-macos`
   reaches React Native 0.86 or later.
   Source: https://microsoft.github.io/react-native-macos/docs/guides/installing-expo-modules
3. CoreBluetooth cannot advertise the mesh tag. Airplane's mesh
   discovery tag is manufacturer data (0xFF, company 0xFFFF, parsed
   from the raw scan record since v0.1.15). On Darwin,
   CoreBluetooth advertising supports local name and service UUIDs
   only: manufacturer data and service data cannot be advertised.
   A Mac could scan phone tags, but it could not advertise the same
   tag format. Full-parity mesh therefore needs a protocol redesign
   (for example service-UUID plus GATT characteristic) and matching
   phone-side discovery changes, not just a Mac port.
   Source: https://deepwiki.com/go-ble/ble/5.1-corebluetooth-bridge-and-device-management
4. No macOS BLE library exists for this stack. `react-native-ble-manager`
   lists iOS and Android only, and no react-native-macos BLE library
   was found. A custom Swift/ObjC TurboModule would be required.
5. Distribution needs her Apple setup. A .dmg distributed outside
   the App Store needs Developer ID signing with hardened runtime,
   notarization, and stapling, or Gatekeeper blocks it on other
   machines. That is the same Apple Developer enrollment that is
   already a NEEDS-USER item for signed iOS, and it is still unordered.

## What a revisit would require, in order

1. A mesh advertisement redesign away from manufacturer data, with
   phone-side discovery changes, so a Mac can both scan and advertise.
2. A React Native upgrade to the Microsoft fork (0.81 or later,
   0.86 or later for SDK 58 macOS support) and migration off the
   Expo modules that have no macOS build.
3. A custom Swift/ObjC BLE TurboModule (scan plus advertise plus GATT).
4. Her Apple Developer enrollment plus Developer ID certificate for
   distribution.
5. Only then: a separate `apps/macos` target, own CI on a macOS
   runner, unsigned `.app` first for proof, then a signed .dmg.

Until items 1 to 4 land, do not start a macOS target and do not put
macOS in any release promise. The next platform item in the queue
is PL3 (iOS signed workflow, code only, gated on the same Apple
enrollment), not a macOS build.
